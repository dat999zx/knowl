# Knowl v1.1 — Intelligence Upgrade Plan

## Context

V1 core is complete: storage, AI pipeline, MCP server, CLI, 24 passing tests.
But V1 is still a "structured note-taking system." These changes turn it into a
knowledge operating system that actually understands project state.

Three features, in dependency order.

---

## Feature 1: Smart `decide` (Conflict Detection)

### The Problem

`knowl decide` does a blind insert. Two contradicting decisions both stay active:

```
knowl decide "Use MongoDB"
knowl decide "Use PostgreSQL"
→ Both are status: active
```

The pipeline's verify+merge stages already handle this for `knowl ingest`, but
`decide` bypasses the pipeline entirely.

### The Fix

Wire `decide` through the verify → merge stages when AI is available.
Fall back to the current blind-insert when AI is not configured.

### Changes

**`src/index.ts` — `decide` command action** (~30 lines changed)

Current flow:
```
collect args → createKnowledgeItem → createKnowledgeCommit → done
```

New flow:
```
collect args
→ build KnowledgeAtom from args
→ try { loadConfig + initAI }
→ if AI available:
    → runVerify(projectId, [atom])
    → runMerge(projectId, verifiedActions, { autoResolveContradictions: true })
    → print result (inserted / updated / superseded)
→ if AI not available:
    → fall back to current blind insert (unchanged behavior)
    → print warning: "⚠️ No AI configured — skipping conflict detection"
```

**`src/mcp/server.ts` — `knowl_decide` tool handler** (same change)

Mirror the same logic: build atom → verify → merge instead of direct insert.

**No pipeline changes needed.** `runVerify` and `runMerge` already support
single-atom arrays. We're just calling them from a new entry point.

### Tests

- Add test: two conflicting decisions → second supersedes first
- Add test: duplicate decision → detected and skipped
- Add test: no AI configured → falls back to blind insert with warning

### Estimated effort: ~1 hour

## Feature 2: Current Truth Derivation

### The Problem

After `knowl decide "Use SQLite" "We will use SQLite for simplicity"`, the
brain state shows:

```
## 💡 DECISIONS
### Use SQLite (ID: f6a7...)
We will use SQLite for simplicity
```

But the ACTIVE STATE section is empty. An agent asking "what database are we
using?" has to scan decisions, architecture, and facts to piece it together.

The spec's vision (§4, §21) is that Knowl maintains **derived current truth**:

```
## ⚡ ACTIVE STATE
database = SQLite
backend = Spring Boot
auth = JWT
```

### Design Decision

Two possible approaches:

| Approach | Pros | Cons |
|---|---|---|
| **A. Auto-derive at read time** — scan decisions + facts + arch and present a summary | No extra storage, always in sync | Expensive read (violates spec §28), needs AI per read |
| **B. Auto-derive at write time** — when a decision/fact is written, extract key=value truths and store as `state` items | Cheap read (just query state items), aligns with spec's "expensive write, cheap read" | Extra write-time AI call, truth can drift if extraction misses |

**Recommended: Approach B** — aligns with the spec's philosophy.

### Changes

**`src/ai/prompts.ts` — new `DERIVE_TRUTH_PROMPT`**

```
You are the truth derivation engine for KNOWL.
Given a knowledge item (decision, fact, or architecture), extract the key=value
truths it implies about the current project state.

Example input:
  Decision: "Use SQLite for the database"
  
Example output:
  [{ key: "database", value: "SQLite", source: "decision" }]

Rules:
- Only extract concrete, factual state (technology, tool, config, version).
- Do NOT extract opinions, reasoning, or goals.
- Use lowercase keys with underscores (database, auth_method, frontend_framework).
- Return empty array if no concrete truth can be derived.
```

**`src/ai/schemas.ts` — new `DerivedTruthSchema`**

```typescript
export const DerivedTruthSchema = z.object({
  truths: z.array(z.object({
    key: z.string().describe('Lowercase key like "database" or "auth_method"'),
    value: z.string().describe('The current value like "SQLite" or "JWT"'),
  }))
});
```

**`src/ai/provider.ts` — new `deriveTruth()` function**

Takes a KnowledgeItem, calls the LLM with DERIVE_TRUTH_PROMPT, returns
`{ key, value }[]`.

**`src/pipeline/merge.ts` — post-merge truth derivation**

After a successful insert or update of a `decision`, `fact`, or `architecture`
item, call `deriveTruth()` on the new item. For each returned truth:

1. Query existing `state` items with a title matching the key
2. If found → update the value (content field)
3. If not found → insert a new `state` item with `title=key, content=value`
4. Add these state changes to the same commit

This means `runMerge` needs an optional AI config parameter (currently it's
pure database). Two options:
- Pass the config into `runMerge` as an optional param
- Create a new `runDeriveTruth` post-processing function called after merge

**Recommended:** Separate `runDeriveTruth()` function called after `runMerge`
in both `pipeline.ts` and the `decide` command. Keeps merge pure.

**`src/pipeline/derive.ts` — new file (~60 lines)**

```typescript
export async function runDeriveTruth(
  projectId: string,
  items: KnowledgeItem[],     // newly inserted/updated items
  dbConnection?: DbConnection
): Promise<DeriveResult>
```

- Filters to only decision/fact/architecture items
- Calls `deriveTruth()` on each
- Upserts state items (update if key exists, insert if new)
- Returns list of state changes made

**`src/pipeline/pipeline.ts` — call `runDeriveTruth` after merge**

```typescript
// After merge
if (mergeResult.insertedIds.length > 0 || mergeResult.updatedIds.length > 0) {
  const changedItems = [...inserted, ...updated]; // fetch from DB
  await runDeriveTruth(projectId, changedItems);
}
```

**`src/core/format.ts` — improve ACTIVE STATE rendering**

Current: renders state items as `### title \n content`

New: renders state items as key=value pairs:

```
## ⚡ ACTIVE STATE
database       = SQLite
backend        = Spring Boot  
auth_method    = JWT
```

### Tests

- Test: `decide "Use PostgreSQL"` → state item `database = PostgreSQL` created
- Test: `decide "Switch to MongoDB"` → state item `database` updated to `MongoDB`
- Test: items without derivable truth (goals, constraints) → no state items created
- Test: `knowl state` output contains key=value active state section

## Feature 3: `npm link` + README

### The Problem

Right now you have to run `node d:\coding\knowl\dist\index.js` every time.
Nobody will use that. Also, no README means nobody else can understand the project.

### Changes

**`npm link`** — run once:

```bash
cd d:\coding\knowl
npm link
```

Now `knowl` works globally:

```bash
knowl init "My Project"
knowl decide "Use React" "React for the frontend"
knowl state
knowl ask "What frontend framework?"
```

**`README.md`** — cover:

1. What Knowl is (2 sentences from the spec)
2. Install (`npm install -g knowl` or `npm link`)
3. Quick start:
   - `knowl init "My Project"`
   - `knowl decide "Use SQLite" "SQLite for persistence" -r "Serverless"`
   - `knowl state`
   - `knowl ask "What database are we using?"`
   - `knowl ingest chat.md`
4. MCP server setup (Claude Desktop / Cursor config snippet)
5. Configuration (`knowl config set ai.provider anthropic`)
6. Available commands table

### Estimated effort: ~30 minutes
