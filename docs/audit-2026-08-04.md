# Knowl audit — 2026-08-04

Seven parallel read-only audits over `fork/mainline-2.16` (25,331 lines, 167 source files).
All seven have reported: 68 findings.
Every finding below was **reproduced or measured against running code**; nothing here is
speculation. Where an agent could only reason from the source it is marked SUSPECTED, and
that distinction is load-bearing — a plausible SUSPECTED finding that turns out false costs
more than it saves.

## How to read this

**Severity**
- `S1` — data loss, silent corruption, or a privacy/execution boundary
- `S2` — silently wrong results the caller cannot detect
- `S3` — cost, latency, noise, or a contract that lies but fails visibly

**Route** — what kind of question the fix actually is. This decides whether outside research
is worth doing, per the router in the `ultimate-research` skill:
- `OWN` — "what does our code do." Already answered by the reproduction. Web search adds
  nothing; go straight to the fix.
- `DOCS` — "how do I use this primitive correctly." Needs the primary source (SQLite docs,
  FTS5 tokenizer reference, Node child_process, the libsql client).
- `CRAFT` — "how do people solve this class of problem." Worth a real two-angle pass:
  established practice plus community failure reports.

**Status** — `FIXED`, `OPEN`, or `SUSPECTED` (needs confirmation before it earns a fix).

## The process

For each finding, in severity order:

1. **Route it** using the `route` column. `OWN` findings skip research entirely — the
   reproduction already is the evidence, and searching the web about our own code is the
   misrouting the skill exists to prevent. `DOCS` findings get the primary source. `CRAFT`
   findings get a real two-angle pass: established practice **and** community failure
   reports, because the failure reports are the only place the trade-offs are honest.
2. **Write the fix with a failing test first**, so reverting the fix fails the test.
3. **Verify against a copy of a real database**, never the live one.
4. **Adversarially review** before it ships: try to refute the fix, and check it did not just
   move the symptom.
5. **Mark it FIXED here** with the commit, so the ledger stays the source of truth.

Findings that share a root cause should be fixed together rather than one at a time — K-25,
K-27 and K-46 are all "the lexical path treats its LIMIT as a filter"; K-28, K-29, K-30 and
K-35 are all "the scoring function mixes incommensurable terms"; K-43, K-44 and K-48 are all
"nothing in this system ever deletes anything."
