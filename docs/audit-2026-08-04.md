# Knowl audit — 2026-08-04

Seven parallel read-only audits over `fork/mainline-2.16` (25,331 lines, 167 source files).
All seven have reported: 70 findings, two of them found during the research pass.
Every finding below was **reproduced or measured against running code**; nothing here is
speculation. Where an agent could only reason from the source it is marked SUSPECTED, and
that distinction is load-bearing — a plausible SUSPECTED finding that turns out false costs
more than it saves.

## How to read this

**Severity**
- `S1` — data loss, silent corruption, or a privacy/execution boundary
- `S2` — silently wrong results the caller cannot detect
- `S3` — cost, latency, noise, or a contract that lies but fails visibly

**Route** — what kind of question the fix actually is. This decides whether outside research
is worth doing, per the router in the `ultimate-research` skill:
- `OWN` — "what does our code do." Already answered by the reproduction. Web search adds
  nothing; go straight to the fix.
- `DOCS` — "how do I use this primitive correctly." Needs the primary source (SQLite docs,
  FTS5 tokenizer reference, Node child_process, the libsql client).
- `CRAFT` — "how do people solve this class of problem." Worth a real two-angle pass:
  established practice plus community failure reports.

**Status** — `FIXED`, `OPEN`, or `SUSPECTED` (needs confirmation before it earns a fix).

| K-10 | `knowl workspace add` rewrites an `${ENV_VAR}` API-key reference into the **literal secret** on disk. `loadConfig` substitutes in memory and the workspace path saves that object back. | K-12 | In-place transcript rewrite that does not shrink the file corrupts pointers: hits resolve to the wrong bodies, some to "unavailable", and the new content is unindexed. | K-13 | Batch ingest that fails partway leaves earlier atoms written with **no commit record**, so the caller is told it failed while rows persist, and blast-radius can never implicate them. | OWN | **FIXED** (lane 6) — the whole batch, including the commit record, now runs in one transaction; overlap lookups and embedding moved after the commit. |
| K-14 | `gc --apply` hard-deletes the *richer* of two title/content twins — reasoning, tags, affectedPaths and evidence are invisible to the duplicate key, and the newer/barer copy wins. | K-15 | The "verbatim duplicate" no-op discards every field except title and content — `affectedPaths`, `sourceCommit`, `tags`, `confidence`, `provenance`, evidence, skill steps — while telling the agent "nothing was lost." `affectedPaths` is what the whole drift system keys on. | OWN | **FIXED** (lane 6, with K-14) — the no-op comparison is deliberately *asymmetric*, not equality: a restatement that merely omits what the store holds still adds nothing, but a barer copy can no longer retire a richer one. |

| K-17 | `withClientTransaction` issues raw BEGIN/COMMIT on the process-wide connection with no mutex; a concurrent write dies on `cannot start a transaction within a transaction`, which is not BUSY so no retry sees it. GC was converted off Drizzle's wrapper so the longest transaction the store opens sits inside the queue. |
| K-18 | `content_hash` is computed over the pre-update value when a field is cleared to `null`, so the stored hash does not match the stored row. Drift and import comparisons trust that hash. | OWN | **FIXED** (lane 6) — the merge feeding the hash now tests `!== undefined`, so "cleared to null" is distinguishable from "not mentioned". |
| K-19 | The batch write path silently drops `conflictKey`/`conflictScope`/`conflictExclusive`, so exclusivity is not enforced for atoms. Latent from MCP today (the schema omits them) but the code comment claims both paths forward them. | OWN | **FIXED** (lanes 6 + 1) — the writer forwards the conflict fields and the `knowl_ingest_atoms` schema exposes them. Merge order mattered: lane 1 before lane 6 would have accepted the fields and dropped them, which is precisely the latent state this row describes. |

| K-20 | `knowl_update` never re-embedded. FTS refreshed by trigger, the vector did not, so a corrected fact stayed semantically retrievable for the claim it no longer made and was invisible for the one it now made. Semantic outweighs lexical by >10×. | OWN | **FIXED** |
| K-21 | `confidence` is unvalidated and is a linear term in the ranking sum. `confidence: 999` on a one-character item ranked it **#1** for an unrelated query. | K-23 | Transcript search returns **zero hits** for any query containing `.`, `-` or `/` inside a word: the tokenizer strips them and glues the pieces into a token FTS5 can never have produced. `index-pass.ts`, `src/transcripts`, `duckprep.xyz`, `GPT-5.6` — all zero. | DOCS | **FIXED** (`719a8cc`, shipped ahead of the lanes) — the query builder quotes the token instead of stripping the punctuation and gluing the pieces together. `duckprep.xyz` went from 1 hit to 316. | K-26 | `composeContext` pins every constraint unranked ahead of the answer, unordered and unlimited. | K-27 | The LIKE fallback truncates by rowid **before** anything ranks it, so it returns the 10 oldest matches of 400 and the item that answers is never handed to the ranker. | OWN | **FIXED** (lane 2) — the LIKE fallback now scores with BM25's saturation and length-normalisation terms *before* the cap, breaking ties by recency rather than rowid. | K-28 | A raw term-frequency count can move a result **38× further than the entire BM25 ordering**, and it is un-normalised for length — precisely what BM25 exists to provide. | K-45 | Vector search is an O(N) full scan with a per-row float32 decode: 173 ms at 2,000 items, **621 ms at 10,000**, paid on every query before model inference. | CRAFT | **FIXED (fu/vector), and the diagnosis in this cell was itself wrong.** It concluded the SQL fetch was 78% and the remedy was to stop moving ~30 MB of BLOBs. That code is `searchKnowledgeEmbeddings` in **`src/store/vector.ts`, which no lane owned.** |

### K-28 / K-29 / K-30 / K-35 — retrieval scoring (RESEARCHED 2026-08-04)

All four reproduced against the real `scoreCandidates`, plus a fifth:

| id | finding | status |
|---|---|---|
| K-70 | The same additive-boost defect on the **vector** path. At a fixed cosine of 0.50, a best-dressed item scores 0.6442 and a worst-dressed one 0.4400 — a **0.204 swing from boosts alone, 96% of the entire 0.401–0.614 legitimate-cosine range the file's own comment documents**. And "did lexical return this at all" is worth 0.0333 while the *whole* lexical ordering is worth 0.0158 — the presence step is 2.1× the ordering it rides on. | **FIXED** (lane 2) — priors became bounded multipliers (≤1) applied after the floor. The swing halved and is now *proportional* at every cosine; before, the score could exceed 1.09 and the presence step was 2.1× the ordering it rode on. |
| K-71 | **Batching changes the stored vector.** A text embedded alone versus in a batch differs by up to **5.4e-2 cosine** (p50 2.3e-2). A batch of 8 or 32 *identical* copies is exact to 4.6e-8, but any heterogeneous neighbour moves it, and length-sorting does not reduce it — which rules out sequence length and points at per-batch dynamic quantisation in the q8 graph. So an atom's vector depended on which neighbours shared its batch: write-time embedding (batch of 1) and `reindex --vectors` (batch of 32) disagreed, and ranking was not reproducible across a reindex. | OWN | **FIXED** (fu/vector) — **and it did change answers, which nobody had established.** Over 120 real `knowl_query` strings recovered from this project's own transcripts, one store, two embedding sets differing only in batch shape: the **shipped ranker's top-10 order changed for 13/120 (10.8%)** and membership for 4/120; the vector half alone moved order for 20/120 and top-1 for 1. It is exactly the 36 of 483 atoms the planner batches (p50 1.90e-2, max 4.79e-2); the other 447 are already alone and bit-identical. Fixed with `maxBatch: 1` on the atom path, **verified free on the whole corpus**: only the 12 multi-item batches change work, and 12 grouped passes cost 2.18 s against 36 single passes at 2.13 s (0.97×). It costs something only on short items — 300 atoms of ~35 tokens run 1.25× slower unbatched — which is the *transcript* path's shape, so that path keeps batching. **fp32 was tested rather than assumed:** it does remove the divergence (max 2.22e-16, exact), confirming per-batch dynamic quantisation as the cause, but costs `embedQuery` 21→64 ms (3.0×), the corpus 286→459 s, resident 1,313→2,250 MB, weights 311 MB→1,226 MB (3.9×), and invalidates every stored vector. Declined: it buys the same exactness `maxBatch: 1` buys for free. |

**The governing finding: additive boosts on a fused rank score are structurally broken, not mistuned.** RRF deliberately destroys magnitude — Cormack's paper says so approvingly, "without regard to the arbitrary scores" — so there is nothing for an additive constant to be a proportion *of*. Elastic hit this in production and wrote it up in exactly our terms: "A rule that slightly promotes a brand for one query can dominate the ranking for another… **This is not a tuning issue; it is a structural property of additive scoring.**"

**The design, in order:**

1. **Move the relevance floor onto the raw cosine, before fusion.** Azure ships this rule verbatim — "filtering occurs before fusing results from different recall sets," and thresholds are "not conducive" to hybrid scores because their ranges are "smaller and more volatile." This fixes K-30 *and preserves the existing 0.30 measurement*, which was taken on raw cosines and would otherwise have to be redone. A stale note can be the only true answer in the store; its age is a reason to rank it lower, never a reason to claim the store knows nothing.
2. **Delete the `text` term rather than retuning it.** `textMatchScore` is an unnormalised re-implementation of the BM25 already computed one layer below — and `search.ts:87` computes `bm25()` and *throws it away*. Return that number instead. Fixes K-28 by deletion.
3. **Fuse by convex combination into `relevance ∈ [0,1]`**, alpha ≈ 0.7, swept. The field has moved this way since RRF: Bruch et al. (TOIS 2023) find convex combination beats RRF in and out of domain and that RRF "is sensitive to its parameters"; Weaviate changed its hybrid default away from RRF in v1.24; OpenSearch publishes RRF at "3.86% lower NDCG@10" than score-based fusion.
4. **Priors become multiplicative and bounded**, applied after the floor. The invariant: *a prior may change where an item sits, never whether it is returned.*
5. **MMR: λ=0.2 is off the map.** Carbonell & Goldstein's λ multiplies *relevance*; they suggest 0.3 for exploring an unfamiliar space and 0.7 once focused. LangChain defaults to 0.5. Our consumer is an agent reading every snippet — it is not exploring. Also remove diversity from the reported score: MMR is a property of the result set, not the item, which is why our scores go negative and non-monotonic.
6. **Surface a calibrated score unconditionally**, not behind `explain`. The consumer is deciding whether to trust memory or go read the files, and a rank cannot distinguish "this is the answer" from "this is the best of a bad lot." Knowl already makes exactly that abstain call internally; it just never shares the evidence.

**Thin evidence, flagged rather than filled:** alpha=0.7 and the prior magnitudes have no source and must be swept. Min-max over a small candidate set forces top→1.0 and bottom→0.0, which is precisely why the floor must stay on the raw cosine. Cross-repo fusion min-maxes BM25 across *different corpora* — incomparable statistics, and no evidence either way on the fix. The FTS5 `bm25()` sign/scale is inferred from `ORDER BY score ASC`, not tested, and the LIKE fallback produces no BM25 score at all. The popular "use lower k for small corpora" advice traces only to blogs; Cormack's own sweep says k "was not critical."

## What remediation found that the audit did not

Recorded because each of these changes how the ledger above should be read.

**One mechanism sat under eleven MCP findings.** The MCP SDK validates the `tools/call`
envelope and never the tool's own `inputSchema`, so `arguments` reached every handler exactly
as written. Each tool had declared its constraints since the day it was added and nothing had
ever enforced one. K-03, 21, 33, 38, 49, 50 and 54 were that single hole wearing seven hats —
which is why the fix is one validator at dispatch, checking the *same* schema object the
client was shown, rather than seven guards.

**A documented table was actively misleading.** `database.ts` recorded the drizzle transaction
failure as "statements *within* a transaction" and listed 2,400 single-statement transactions
as clean. Re-measurement inverted it: the variable is the count of `db.transaction()` calls
(threshold 800–1000), and one transaction holding 10,000 statements is clean. The old reading
implied a big transaction was dangerous and many small ones were safe — backwards, and it
would have steered every future batching decision the wrong way.

**Two findings were wider than written**, both discovered only by trying to fix them. K-07 is
not a gap on `supersedes`: `knowl_store`, `knowl_ingest_atoms` and `knowl_decide` had no
ownership guard at all. K-08's obvious fix does not cover the ledger's own "2 of 5 repos"
example, because a manifest entry with no local path never becomes a peer and so was invisible
to the guard entirely.

**A SUSPECTED finding was wrong, and saying so was the deliverable.** K-56 does not reproduce.
The reproduction attempt is what corrected the table above.

**Owned by no lane, still open** — these need a home before the audit can be called closed:
- K-58's real fix is at `portability.ts:116` plus an export-format bump; the workspace layer
  cannot derive an identity the database never stored.
- `recordDecisionDirect` (`knowledge-actions.ts`) calls `resolveDuplicate` without a held
  payload, so `knowl decide` still compares fewer fields than every other write path.
- The store-level `confidence` clamp: K-21 is bounded at the MCP boundary only, so CLI and
  hook writes still bypass it.
- K-55 needs a `releaseClient(dbPath)` primitive; the lane that owns the pool had no caller
  for it and declined to add a speculative one.
- Four `db.transaction()` callers remain in long-lived processes: `assertions.ts`, `drift.ts`,
  `pipeline/merge.ts`, `pipeline/derive.ts`.

**Operational, learned the hard way:** a fresh git worktree has no `dist/`, and ~13 CLI suites
spawn `node dist/index.js` — every lane's first full run showed ~55 failures that were pure
build absence. `npx tsup` first. Verification also has to happen somewhere other than
`D:\Code\knowl`, whose `dist/` is the live global install for every repo on this machine.

## The process

For each finding, in severity order:

1. **Route it** using the `route` column. `OWN` findings skip research entirely — the
   reproduction already is the evidence, and searching the web about our own code is the
   misrouting the skill exists to prevent. `DOCS` findings get the primary source. `CRAFT`
   findings get a real two-angle pass: established practice **and** community failure
   reports, because the failure reports are the only place the trade-offs are honest.
2. **Write the fix with a failing test first**, so reverting the fix fails the test.
3. **Verify against a copy of a real database**, never the live one.
4. **Adversarially review** before it ships: try to refute the fix, and check it did not just
   move the symptom.
5. **Mark it FIXED here** with the commit, so the ledger stays the source of truth.

Findings that share a root cause should be fixed together rather than one at a time — K-25,
K-27 and K-46 are all "the lexical path treats its LIMIT as a filter"; K-28, K-29, K-30 and
K-35 are all "the scoring function mixes incommensurable terms"; K-43, K-44 and K-48 are all
"nothing in this system ever deletes anything."
